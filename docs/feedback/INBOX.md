# INBOX.md — 사용자 피드백 / 최우선 지시

이 파일은 사용자(설계자)가 AI에게 남기는 지시와 피드백을 담는다.
**매 이터레이션 시작 시 가장 먼저 읽고, 다른 무엇보다 최우선으로 반영한다.**

## 사용 규칙

- 새 지시는 "남은 이슈 (미처리)" 섹션 맨 위(가장 최근이 위)에 날짜와 함께 추가한다.
- AI가 항목을 반영했으면 지우지 말고 `[처리됨 - YYYY-MM-DD]` 를 앞에 붙여 표시하고,
  **반드시 실제로 해당 섹션("처리됨" 또는 "부분 처리됨")까지 옮긴다** — 태그만 붙이고
  "남은 이슈" 섹션에 그대로 두지 말 것. (히스토리를 남겨야 나중에 "이 결정이 왜
  이렇게 됐는지" 추적 가능. 2026-09-09에 태그만 붙고 이동을 안 해서 몇 개가 계속
  "남은 이슈"에 남아있던 사고가 있었음 — 반복하지 말 것.)
- 처리 못 하거나 애매한 항목은 `docs/STATUS.md`의 "알려진 이슈 / 막힌 것"에 사유를 남기고,
  이 파일의 항목 앞에 `[보류 - 사유]`를 붙인다.
- 세 섹션 안에서는 각각 날짜 최신순(위쪽이 최근)으로 정렬한다.
- **"처리됨" 섹션이 12개를 넘으면**, 가장 오래된 항목들을(12개가 될 때까지) 잘라서
  `docs/INBOX_ARCHIVE.md` 맨 위에 옮겨 적어라(파일 없으면 새로 만들 것). 내용을
  요약하거나 버리지 말고 그대로 옮기기만 한다 — 이 파일은 매 이터레이션 통째로 읽는
  파일이라 계속 누적되면 읽기 비용이 무한정 커진다(STATUS.md가 2026-09-07에 275KB까지
  불어나 docs/STATUS_ARCHIVE.md로 정리한 것과 같은 이유). "부분 처리됨"은 여전히
  진행 중인 항목으로 취급해 archive하지 않는다.

    창이 OS 포커스를 받기 전 `grab_focus` 타이밍, ScrollContainer/3D 뷰포트가 방향키 소비, `ui_accept`(스페이스) 처리 순서, 마우스 hover와 포커스 상태 충돌. **반드시 실제 OS 레벨 키 입력으로 재현**하라: PowerShell에서 게임 창(`Godot_v4.7.2-stable_win64.exe`)을 `AppActivate`/`SetForegroundWindow`로
    전면에 두고 `SendKeys`(또는 `SendInput`)으로 ←→↑↓/Space/Enter/Esc를 보낸 뒤 포커스/화면 결과를 `VisualQA` 캡처 또는 로그로 확인(엔진 주입 방식 금지). 화면마다 "첫 방향키 입력에 즉시 반응하는가"를 표로 만들고 전부 고친다.
  - **요구 흐름**: 캐릭터 선택 화면에서 ←→↑↓로 캐릭터 카드 이동, Space로 선택 → **포커스가 자동으로 시작 스킬 슬롯으로 이동** → ←→로 스킬 선택, Space로 확정 → **포커스가 "던전 입장" 버튼으로 이동** → Space로 입장. Esc는 한 단계 뒤로(스킬 선택 → 캐릭터 선택).
    각 단계가 화면에서도 보이게(현재 단계 강조 또는 작은 단계 표시 ①캐릭터 ②시작 스킬 ③입장).
  - (10) **던전 시작 버튼을 "던전 입장" 버튼으로 재디자인**: 텍스트가 이상하고(현재 라벨/크기가 안 맞음), 색상도 어울리지 않는다 → 라벨 "던전 입장", 선택한 캐릭터 퍼스널 컬러 accent의 주(primary) 버튼 스킨(UIKit), 하단 중앙 적절한 크기(텍스트가 버튼 안에 여유 있게),
    포커스/호버/눌림 상태 구분. 캐릭터를 선택하기 전에는 비활성(회색)으로.
  - 테스트: 위 3단계 흐름을 키 시퀀스로 진행해 `RunState`(선택 캐릭터/시작 스킬)와 씬 전환이 일어나는지 + 가능하면 실제 OS 입력 하네스(스크립트)로도 1회 검증하고 그 방법을 `docs/STATUS.md`에 문서화해 이후 이터레이션이 재사용하게 한다.

  **Q-4a. 던전 맵 선택지 정리 (원문 12, 13, 14)**

  - 테스트: 모든 방 선택지 버튼의 rect 크기가 같은지, 보상 칩이 버튼 자식 안에 있는지, 방 카드에 보상 칩이 없는지. 캡처로 여러 방 구성(전투만/전투+이벤트/상점 포함/정예) 확인.

  **Q-7. 스킬 효과 도식화 (원문 3) — (a) 문법/데이터 → (b) 렌더러 → (c) 적용**
  - 목표: **모든 스킬의 설명 위에 효과를 이미지/도형으로 도식화**해서 글을 읽지 않아도 효과를 빠르게 알 수 있게 한다. 현재 [발견/미발견] 배지가 있던 자리(카드 상단)에 이 도식을 띄운다. **기호는 최대한 적게** 쓰고 필요하면 스킬 자체를 리디자인(효과를 단순화)해도 된다.
    **미발견 스킬은 도식 대신 해금 조건만 보여준다(스킬 정보 공개 금지).**
  - **(a) 도식 문법 + 데이터**: 최소 기호 집합을 정의 — 주사위(공격/방어/이벤트 색 구분), 개수 비교(>, =), 조건(HP 절반 이하, 첫 턴, 전투 시작, 눈금 N개 등 아이콘+값), 화살표(→ 효과), 수치 배지(+1, +2, ×2), 대상(공격 주머니/방어 주머니/이벤트 주사위), 지속(첫 턴 한정/매 턴/1회), 확률/재굴림(순환 화살표), 골드 등.
    스킬마다 **도식 데이터 `diagram`(조건 칩 → 효과 칩 배열)** 을 `SkillPool`에 데이터로 둔다(하드코딩 렌더 분기 금지). 현재 37종 전수 작성, 한 도식당 기호 최대 4~5개 목표. 도식으로 표현이 어려운(설명이 복잡한) 스킬은 효과를 단순화하는 리디자인 후보로

  **Q-8. 스킬 레어리티 + 전설 스킬 (원문 5) — (a) 레어리티 체계 → (b) 효과 차등 → (c) 전설 스킬 구현 → (d) 마무리**
  - 요구: **스킬에도 레어리티를 주고 효과를 다르게 한다.** **양상이 크게 바뀌는 강력한 스킬을 세 개씩 만들어 가장 높은 레어리티를 부여하고, 이 등급 스킬은 한 런에 하나밖에 못 가진다(설명에도 적혀 있어야 함).**
    해석(모호하면 이렇게 진행하고 STATUS.md에 가정 명시): **"세 개씩" = 캐릭터마다 3개씩**(8명 × 3 = 24종 전설 스킬, 해당 캐릭터 전용). 만약 이터레이션이 규모상 한 번에 불가능하면 (c)를 캐릭터 2명씩 쪼개 여러 이터레이션으로 나눠 진행.
  - **(a) 레어리티 체계**: 등급 4단계(예: 일반 / 희귀 / 영웅 / 전설 — 이름은 구현 판단, 아이템 S/A/B/C 등급과 구분되게 스킬 전용 표시)와 색, 모든 기존 스킬 37종에 등급 배정(기본 스킬=일반, "+" 강화판=상위 등급 등 기준을 표로 정리), 카드 프레임/도감/도식/팝업에 등급 표시(아이콘 테두리색 + 작은 텍스트).

  스킬/성장 정책(F-5)/시뮬 규칙 자체 — 측정 도구를 바꿔 숫자를 맞추면 의미가 없다.
