> AI 관점(구조·로그·값 검증)이 아니라 **사람이 실제 화면을 볼 때의 인지**다."

캐릭터 선택 · 던전 맵 · 전투 · 이벤트(특수 이벤트/스토리 이벤트) · 상점 · 승리 보상 ·

## 2. 배경 대비 기준

WCAG 2.0 기준을 그대로 쓴다(`CharacterTheme.contrast_ratio()`가 이미 이 공식을 쓰고
있음 — 새 기준이 아니라 기존 코드가 이미 따르던 기준을 전 화면 요소로 넓히는 것):

- **일반 글자(본문/캡션)**: 배경 대비 **4.5 : 1 이상**
- **큰 글자(18px 이상 또는 14px+ 굵게)**: 배경 대비 **3 : 1 이상**
- 장식(테두리/배지/아이콘)은 이 기준 밖이지만, 장식 위에 글자가 "얹히는" 경우
  (버튼 안 텍스트가 장식 텍스처 위에 그려지는 경우 등)는 그 지점의 **실측** 대비가
  이 기준을 만족해야 한다 — 평균색이 아니라 글자가 실제로 겹치는 자리의 색.

### 2-1. 측정 도구

`code/qa/pixel_contrast.gd` (신규, 이번 이터레이션 추가) — Godot 헤드리스 스크립트.

```
# 캡처 PNG의 사각 영역에서 밝기를 읽어 대비비 계산
godot4 --headless --script code/qa/pixel_contrast.gd -- <png> <x,y,w,h,label> [...]
#   라벨이 text:<name> 이면 그 영역의 "가장 밝은 픽셀"(글자 중심부로 간주),
#   bg:<name> 이면 "가장 어두운 픽셀"이 아니라 평균(깨끗한 배경 영역을 호출부가 직접
#   골라 넣어야 함)을 쓴다 — 같은 <name>끼리 자동으로 짝지어 대비비를 출력.

# 코드의 색 상수끼리 바로 계산(캡처 없이)
godot4 --headless --script code/qa/pixel_contrast.gd -- --rgb <r,g,b,r,g,b,label> [...]
```

안티앨리어싱된 작은 한글 글자는 "영역 평균"으로 재면 배경 픽셀이 섞여 실제보다 어둡게
나온다(1회차 측정에서 확인된 함정 — 평균 기준으로는 "일반" 필터 칩 글자도 1.66:1로
나와 조작자가 직접 본 인상과 어긋났음). 그래서 **글자 쪽은 영역 안 최댓값(가장 밝은
픽셀 = 글자 획의 핵심)**, **배경 쪽은 글자가 없는 깨끗한 인접 영역의 평균**을 쓰는
방식으로 재측정했다 — 아래 표가 그 결과.

### 2-2. 측정 결과

| 요소 | 글자색 (실측/코드) | 배경색 (실측/코드) | 대비비 | 판정 |
| --- | --- | --- | --- | --- |
| **몬스터 도감 필터 줄 "전체"(티어, 활성 상태)** — `monster_codex_before.png` (648,90,26,16) vs (647,78,30,9) | 실측 피크 `rgb(0.290,0.290,0.290)` | 실측 평균 `rgb(0.121,0.121,0.125)` | **1.86 : 1** | **FAIL** (사용자가 직접 지목한 사례) |

| `combat_test` 몬스터 특성 줄(코드 상수) | `Color(0.7,0.7,0.72)` | `panel_bg≈Color(0.1,0.1,0.13)` | 8.28 : 1 | PASS |

| `DeckPanel` 빈 상태 라벨(코드 상수) | `Color(0.6,0.6,0.6)` | `panel_bg≈Color(0.1,0.1,0.13)` | 6.10 : 1 | PASS |

**결론**: "코드가 명시적으로 지정한 단색 글자/배경" 조합은 전부 기준을 통과한다
(`CharacterTheme`의 `_ensure_text_contrast()`가 애초에 이걸 보장하도록 설계돼
있음 — K-3 때부터 있던 장치). **실패하는 지점은 코드가 아니라 장식 이미지 스킨
(`resources/ui/button/*`, `badge/*`) 위에 글자가 얹히는 자리** — 스킨 텍스처 안에
밝기가 들쭉날쭉한 장식(보석/날개 하이라이트)이 있어서, `UIKit.contrasting_text_color()`
(평균 accent색 기준으로 흑/백 중 더 나은 쪽을 고르는 함수)가 전제하는 "단일 배경색"
가정이 실제 렌더링에서는 깨진다. 즉 **코드 레벨 대비 보장 로직 자체는 정상 동작하지만,
그 보장이 가정하는 "배경은 단색"이 장식 텍스처 앞에서는 성립하지 않는다** — 이게
S-2("버튼 장식이 글씨를 가려 읽기 어렵다")의 실측 근거다. 본 구현 때 선택지는 (a)
글자 바로 뒤 영역만은 장식 없이 단색(또는 낮은 채도)으로 비워두는 스킨 규칙을
정하거나, (b) 글자에 외곽선(outline)을 입혀 배경 밝기 변화에 덜 민감하게 만드는 것 —
이 문서는 기준만 정하고 결정은 보류(아래 "장식 한도" 절 참고).

## 3. 정보 위계 3단계

모든 화면 요소는 아래 3단계 중 하나에 속해야 하고, 시각적 강도(크기·대비·채도·여백)가
그 순서를 따라야 한다 — 3순위가 1순위보다 크거나 선명하면 위계 위반이다.

| 순위 | 정의 | 시각 처리 | 예 |
| --- | --- | --- | --- |
| **1순위** | 지금 당장 해야 할 일, 그 결정에 필요한 핵심 수치 | 가장 크고(강조~표제급), 가장 높은 대비, 화면에서 시선이 먼저 닿는 위치(좌상단 또는 중앙) | "던전 입장" 버튼 활성 상태, 전투 중 공격/방어 합계, HP 숫자, 지금 선택 가능한 카드 |
| **2순위** | 1순위를 이해하는 데 돕는 보조 정보 | 본문~소본문 크기, 중간 대비, 1순위 옆/아래에 배치 | 카드 설명 한 줄, 캐릭터 능력치 칩, 몬스터 특성 줄 |
| **3순위** | 분위기를 돕는 장식 | 가장 흐리게(낮은 채도/낮은 대비), 가장 작게, 절대 1·2순위보다 먼저 읽히면 안 됨 | 패널 테두리 장식, 제목 좌우 보석 장식, 비네트, 구분선 |

**검증 방법(본 구현 때 적용)**: 화면을 640x360으로 축소하거나 흐리게(가우시안 블러)
처리했을 때도 1순위 요소의 위치와 의미가 먼저 식별돼야 한다 — 이 문서 7절의
"사람 눈 검증"이 이 기준으로 각 시안을 확인한다.

## 4. 장식 한도

INBOX S-6("장식이 정보보다 앞서 보인다") 반영. 아래는 **장식 요소**(정보를 담지 않는
순수 시각 요소 — 테두리 두께, 반짝임/빛 효과, 장식 아이콘)에 거는 상한이다.

| 항목 | 한도 | 현재 상태 |
| --- | --- | --- |
| 패널 테두리 두께 | 1~2px | `UIKit.SECTION_BORDER_WIDTH = 1` — 이미 기준 안 |
| 버튼 테두리 두께(보조 버튼) | 2px 이하 | `style_secondary_button` border_width 2 — 기준 안(상한선) |
| 패널 그림자 크기 | 6px 이하, 알파 0.35 이하 | `SECTION_SHADOW_SIZE=6`, `SECTION_SHADOW_COLOR.a=0.35` — 기준 안 |
| 장식 채도(비네트/강조 테두리 제외 순수 장식) | HSV 채도 0.6 이하 | 버튼 스킨(resources/ui/button/*) 장식부 채도는 실측 미확인 — 아트 쪽 "더 얇고 차분한 UI 키트" 요청과 함께 재점검 필요 |
| 글자 위에 직접 겹치는 장식(보석/하이라이트) | **금지** — 장식은 글자 영역을 피해 배치하거나, 글자 영역만 장식 없는 단색 패드를 둔다 | 2절에서 실측 위반 확인(필터 칩 "전체") |
| 포커스 강조 테두리 두께 | 2~3px(`FocusNav`가 이미 이 범위) | 기준 안 |
| 빛/글로우 효과(예: 어두운 몬스터 림 라이트) | 특정 조건(예: 휘도 임계값 미만)에서만, 상시 아님 | `DARK_PORTRAIT_LUMINANCE_THRESHOLD` 조건부 — 기준 안 |

**원칙**: 장식은 "이게 뭔지 모르겠지만 예쁘다"가 아니라 "이게 뭔지 1순위/2순위를 가리지
않으면서 분위기를 돕는다"여야 한다. 장식 하나를 지워도 정보 전달에 지장이 없어야 하고,
장식이 사라졌을 때 레이아웃이 깨지면(예: 텍스트가 장식이 차지하던 공간으로 밀려야 함)
안 된다 — 즉 장식은 항상 "있어도 되고 없어도 되는" 오버레이여야지, 레이아웃 결정 요소가
되면 안 된다(필터 칩 사례가 정확히 이 원칙 위반 — 장식 아이콘이 버튼 폭의 절반 이상을
차지해 글자 자리를 좁힌다).

## 5. 간격·정렬 격자

**8px 단위 격자**를 기준으로 삼는다(이미 코드 다수가 8의 배수를 쓰고 있어 — 예:
`UIKit.SECTION_CORNER=8`, 섹션 separation 6~8 등 — 새 규칙이라기보단 느슨하게 지켜지던
관행을 명문화). 규칙:

- Control의 `position`/`size`, 컨테이너의 `separation`/`content_margin`은 8의 배수를
  기본값으로 한다(4의 배수까지는 허용 — 작은 아이콘 패딩 등 8이 너무 큰 경우).
- 화면 가장자리 여백은 최소 16px(8의 2배).
- 패널 내부 콘텐츠 여백(content_margin)은 최소 8px.
- 버튼 사이 간격은 최소 8px(겹침 방지 최소 여유).

이 격자는 "자로 잰 듯 딱 맞아야 한다"는 뜻이 아니라, 좌표를 잡을 때 임의의 숫자
(예: 13px, 27px) 대신 격자에 맞는 숫자로 반올림해 **화면 전체의 정렬감**을 만드는
용도다.

## 6. 아이콘 비율·크기 규칙

### 6-1. 원칙

모든 아이콘은 **정사각 슬롯 안에 원본 비율을 유지**한 채로 그려져야 한다(늘림 금지).
슬롯보다 원본 비율이 다르면(예: 세로가 긴 원화) **크롭하지 않고 여백(letterbox)으로
맞춘다** — Godot `TextureRect`라면 `stretch_mode = STRETCH_KEEP_ASPECT_CENTERED` +
`expand_mode = EXPAND_IGNORE_SIZE`가 정확히 이 동작이다(이미 `UIKit`의 `icon_texture`
호출부 일부가 이 조합을 씀 — 예: `make_section`의 `icon_rect`).

### 6-2. 실제 위반 원인(코드 레벨, 2026-10-28 확인)

`RewardIcon`(`code/scenes/reward_icon.gd`)과 `FamilyIcon`(`code/scenes/family_icon.gd`)은
`TextureRect`가 아니라 `Control` + `_draw()`를 직접 쓰고, 이미지 아이콘을 그릴 때
`draw_texture_rect(tex, Rect2(Vector2.ZERO, size), false)`로 **그 Control의 `size`에
그대로 꽉 채워** 그린다 — Godot의 `draw_texture_rect`는 비율 유지 옵션이 없어서,
`size`가 정사각이 아니면 그대로 눌리거나 늘어난다. 두 클래스 모두
`custom_minimum_size`는 정사각(18x18/20x20/24x24)으로 주지만, `HBoxContainer`
안에서 세로 `size_flags`가 기본값(`SIZE_FILL`)이라 **행 전체 높이에 맞춰 세로로
늘어날 수 있다** — 던전 맵 선택지 줄(`dungeon_map.gd:452` 전후, `_make_reward_icon`/
`FamilyIcon` 생성부)이 이 경로를 그대로 타서 INBOX S-7(a) 캡처의 "세로로 길쭉한
아이콘"이 나온다.

**본 구현 때 고칠 방향(이번엔 적용 안 함, 설계만)**: `UIKit`에 공용 헬퍼
`draw_icon_keep_aspect(control: Control, tex: Texture2D, slot: Rect2) -> void`를
추가해 — slot 안에서 tex 원본 비율을 유지하는 letterbox 사각형을 계산해
`draw_texture_rect`에 넘기고, `RewardIcon`/`FamilyIcon`의 `_draw_image_icon()`류가
전부 이 헬퍼를 거치게 한다. 추가로 두 클래스 모두
`size_flags_vertical = Control.SIZE_SHRINK_CENTER`(가로도 동일)를 기본값으로 둬서
애초에 컨테이너가 강제로 늘리지 못하게 막는 것도 함께 필요(둘 다 해야 "컨테이너가
늘려도 안 깨짐" + "늘어날 일 자체를 없앰"이 겹으로 보장됨).

### 6-3. 테스트(본 구현 때 추가)

"아이콘 노드가 정사각 슬롯에서 원본 비율로 그려지는지" 결정적 검증 — `dice_test.gd`에
`UIKit.draw_icon_keep_aspect()`를 비정사각 slot(예: 40x20)과 비정사각 텍스처(예:
64x32)로 호출해, 반환/기록된 렌더 사각형의 가로:세로 비율이 텍스처 원본 비율과
오차 없이 일치하는지 순수 함수 단위로 확인한다(물리/화면 없이).

## 7. 상태 메시지 바 공통 컴포넌트 규격 (S-3)

### 7-1. 배경

캐릭터 선택 화면의 "① 캐릭터 → ② 시작 스킬 → ③ 던전 입장" 단계 표시는 **제거**한다
(이유를 알기 어렵고, 실제로 뭘 해야 하는지 알려주지 않음). 대신 "지금 뭘 해야 하는지"를
화면 안에서 직접 보여주는 **상태 메시지 바**를 공용 컴포넌트로 만든다.

### 7-2. 규격

- **위치**: 화면 하단 고정(전투/던전 맵처럼 하단에 다른 고정 UI가 있으면 상단 고정으로
  예외) — 화면마다 임의 위치에 두지 않고 "항상 같은 자리"를 지킨다.
- **크기**: 폭은 화면 전체 폭 - 좌우 여백(32px씩), 높이 40~48px.
- **표시 조건**: 조건이 충족되지 않은 동안만 보이고, 충족되면 **사라진다**(토스트처럼
  몇 초 뒤 자동으로 없어지는 게 아니라, 조건 자체가 해소되면 즉시 숨김 — 예: "시작
  스킬을 선택해 주세요"는 스킬을 고르는 순간 사라짐).
- **글자**: 본문 크기(14~15px), 배경 대비 4.5:1 이상(2절 기준 그대로 적용).
- **강조**: 배경색은 `panel_bg`보다 한 단계 밝은 경고색 계열(예: 노랑/주황 계열 저채도)
  — 3순위 장식이 아니라 2순위 보조 정보이므로 장식 한도(4절)보다는 눈에 띄어야 하지만,
  1순위(핵심 버튼/수치)보다 작아야 한다.
- **인터페이스**: `UIKit.make_status_bar(parent, text, character_id) -> Control`
  형태의 공용 함수로 설계(본 구현 때 추가) — 호출부는 `text`만 갈아끼우면 됨. 같은
  컴포넌트를 던전 맵/이벤트/승리 보상 화면에도 재사용(예: "상점에서 살 게 없으면 뒤로
  가기를 누르세요", "보상을 하나 고르세요").
- **비활성 버튼과의 관계**: 상태 메시지 바는 "왜 안 되는지"를 설명하고, 그 원인이 되는
  버튼(예: "던전 입장")은 동시에 `disabled` 상태로 표시해 **이중으로** 알려준다(메시지만
  있고 버튼이 눌리는 것처럼 보이면 혼란).

## 8. 화면별 키 매핑 표 (S-8)

기존 `FocusNav`(DESIGN.md "조작" 절)는 "화면 하나 안의 모든 포커스 가능 버튼을 한 줄
체인으로 연결"하는 모델이다. S-8이 지적한 문제(캐릭터 목록에서 위/아래가 목록 밖
상단 버튼으로 새어나감)는 이 "한 줄 체인" 모델이 **"영역(지역) 단위로 묶이지 않고
화면 전체가 평평한 한 줄"**이기 때문에 생긴다. 아래는 화면마다 "영역"을 먼저 나누고,
영역 안/영역 사이 이동을 분리하는 설계다 — 본 구현 때 `FocusNav`에 "영역(region)"
개념을 추가해야 한다(예: `FocusNav.chain_region(controls, wrap=true)`로 영역 내부를
닫힌 루프로 묶고, 영역과 영역 사이는 별도의 "영역 진입/이탈" 엣지로 연결).

**공통 규칙**: 화면 공간 배치와 방향키 방향이 일치한다 — 왼쪽에 있는 영역은 왼쪽 키로
진입, 위에 있는 영역은 위쪽 키로 진입. 영역 안에서는 그 영역의 자연스러운 배치 축
(세로 목록=위/아래, 가로 카드 줄=좌/우)으로만 순환한다. 확정은 어디서나 스페이스/Enter,
취소/뒤로는 어디서나 Esc(오버레이가 열려있을 때) 또는 지정된 "뒤로" 버튼.
